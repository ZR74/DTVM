PR507 WORK SUMMARY

把一条 legacy CALL 回归，修成可复现、可对照、可回归的正确性修复

PR507 的主线不是性能优化，而是围绕一条真实历史交易的 legacy CALL 回归，把问题从“偶发分叉”整理成“可独立复现、可在 DTVM-only 环境运行、并且能稳住 interpreter / multipass 一致性”的完整闭环。 核心修复点在于：非 lifted block 边界上的 EVM 栈状态和实例元数据必须同步，不能让过期的逻辑栈污染后续 CALL 的受体、gas 和 provenance。

legacy CALL 回归 跨 block 栈同步 interpreter / multipass 对照 dtvmapi DTVM-only 回放 fixture / schema 加固

一句话结论

PR507 解决的是“历史 legacy CALL 在不同执行路径上行为不一致”的正确性问题。 它做了两件事：一是补齐可复现的回归测试和 fixture，二是修正 compiler frontend 在非 lifted block 边界上的栈状态同步逻辑。

发现了什么问题

1. 跨 block 的逻辑栈状态会失真

在 lifted / non-lifted 的块边界上，tracked stack 没有稳定地写回或重新加载到 `EVMInstance`，dead block 在某些终止后还可能被重复 finalize。

  • 非 lifted 入口可能拿到过期的 stack 元数据。
  • materialize 后的 hidden prefix 容易和实例态脱节。
  • CALL 的 recipient / gas / provenance 可能被旧栈污染。

2. 旧回归样本不够独立

原始 legacy CALL 回归依赖较重的外部链上下文，DTVM-only 的回放能力不足，fixtures 也没有把 `BLOCKHASH` 相关环境完整表达出来。

  • 没有稳定的 `dtvmapi` 直跑路径。
  • fixture 缺少 block hash 及其覆盖映射。
  • 测试对 JSON 结构的校验也偏松。

为什么要修

避免 interpreter / multipass 分叉

同一条交易在两条路径上如果拿到不同的 CALL 受体或不同的栈状态， 就不再是“性能差异”，而是实打实的语义不一致。

防止历史回归被掩盖

没有独立 fixture，问题只能靠外部环境碰运气复现，修复后也很难确认是否真的稳定。

避免错误向后传播

过期的 stack provenance 一旦进入后续 block，会把后面的 CALL、JUMP、POP 都带偏，问题会从单点扩大成链式故障。

让回归测试变成长期护栏

这个 PR 最重要的价值之一，是把一次故障整理成以后每次改 compiler 都能重新跑的回归资产。

修复方法

编译器侧

  • 在非 lifted 入口重新从 `EVMInstance` 加载 tracked stack 元数据。
  • 在 materialize 时把 tracked stack 的元数据同步回实例态。
  • 新增 `CurrentBlockNeedsFinalize`，避免 terminator 后重复 finalize。
  • 把 trap 后的块清理收敛到统一路径，防止“死块二次收尾”。

测试与 fixture 侧

  • 新增 standalone legacy CALL repro 及 runner。
  • 把样本扩展为 DTVM-only 可回放的数据包。
  • 补 `block_hash` / `block_hashes`，覆盖历史 `BLOCKHASH` 依赖。
  • 通过 `dtvmapi` 跑 interpreter / multipass 双路径对照。
  • 加强 fixture 解析、选项设置和状态码检查。

如果不修会怎样

  • 同一笔交易在 interpreter 和 multipass 上可能出现不同的 CALL 结果。
  • 历史 legacy CALL 回归可能只能“偶尔复现”，难以稳定定位。
  • 后续 block 会继承错误的栈前缀，问题会沿着 CFG 继续放大。
  • 修复前后的对照没有护栏，新的 compiler 改动可能再次引入同类错误。

结果

技术结果

PR507 把 legacy CALL 的问题从“现象”变成“机制”：问题不只是某条交易坏了， 而是非 lifted block 的栈状态和实例态没有对齐。

工程结果

现在有了可以长期保留的回归 fixture、dtvmapi 路径和 compiler 级别的对照测试， 后续再改 SSA / 栈传播逻辑时，有地方直接验收。

注：这份总结强调的是 PR507 的正确性修复链，不是性能优化结论。 如果后续要单独写性能分析，应和这条回归修复线分开看。
