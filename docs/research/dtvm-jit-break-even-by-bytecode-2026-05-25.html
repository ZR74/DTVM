同一 Bytecode 的 JIT 回本分析

这份报告关注的是：对同一合约（同一 bytecode），需要执行多少次，multipass JIT 才能摊平掉一次性的编译成本。实验方法是：选取 200 交易里高频 bytecode 组的代表交易，分别测冷启动单次与同进程额外执行 2000 次的 multipass / interpreter，然后用 (benchmark_wall - cold_wall) / N 估算 steady-state 单次成本。

Interpretation

  • 如果 `Saving / Exec` 为正，说明同一进程下多次执行时，JIT 每次执行已经比 interpreter 便宜；这时 break-even = 编译成本 / 每次节省。
  • 如果 `Saving / Exec` 为负，说明当前代表交易上 interpreter 反而更便宜，这种 bytecode 组在当前实现下没有长期回本点。
  • 回本次数大的组，通常是因为编译成本虽然不高，但每次执行只省了很少的一点；这种场景需要非常高的复用率才值得 JIT。
  • 回本次数小的组，说明 bytecode 结构更适合 JIT：编译成本不高，steady-state 执行收益也足够明显。
  • 这份结果是按“同 bytecode 代表交易”估计的，不是对所有 calldata / state 组合的严格上界。它更适合作为 JIT profitability gate 的经验依据。

What To Do With This

  • 对 break-even 低于 200 次的 bytecode 形态，可以考虑更积极地启用 JIT。
  • 对 break-even 高于 800 次甚至不存在的组，应该更早走 interpreter 或更保守的 profitability gate。
  • 如果要把 `SSA On` 作为默认路径，必须单独重做同样的 break-even 分析；当前这份只反映 `multipass + current off build`。
