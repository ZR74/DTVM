  • Note: this report uses evmone-t8n as a cold-run state-transition baseline. It does not provide a same-process steady-state harness equivalent to DTVM's internal benchmark mode, so the evmone comparison is intentionally limited to cold wall time and transaction-level gasUsed. DTVM correctness parity was established separately on the same 200-transaction corpus for SSA off vs SSA on.

Optimization Readout

  • SSA on still needs a stricter profitability gate on datasets where on wall stays above both off and evmone, especially if the JIT mean already improved but end-to-end wall did not.
  • The DTVM interpreter baseline is materially faster than both DTVM multipass paths on cold start, so startup, module loading, and runtime setup overhead remain first-order costs. This gap should be optimized independently of SSA codegen.
  • If cow_settlement, erc4337_bundle, and uniswap_v3_swap improve under SSA on but still trail the interpreter and evmone, the next gains are more likely in runtime helpers, host calls, and startup overhead than in the SSA stack/value model itself.
  • erc20_transfer remains the clearest negative-profitability zone: SSA on reduces JIT time but substantially worsens wall time. Keep it as the first target for gate tightening and compile-path trimming.
  • The gap to evmone on cold wall should be treated as a full-stack DTVM overhead gap, not an SSA-only gap. Use it to prioritize startup/load/instantiation trimming separately from SSA codegen tuning.
