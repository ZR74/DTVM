SSA=ON 待修复问题

这份报告只回答一个问题：在当前 DTVM 上，ZEN_ENABLE_EVM_STACK_SSA_LIFT=ON 还存在哪些明确待修复的问题，它们在 40 条真实主网交易 replay 上如何体现。

一句话结论：SSA=ON 当前至少同时存在两类 P0 问题：一类是 phi / verifier 相关的无效 MIR，另一类是 没有 verifier error 但仍然发生的语义或状态码分叉。在这两类问题清零之前，SSA 还不能被视为可上线的性能优化项。

证据边界

  • off 基线：data/tx_replay_benchmarks/hotset_multipass_cold_after_internal_call_journal_20260519 的 40 条全量基准回放。
  • off 当前 spot-check：6 条高风险交易，6/6 与历史 off 返回码一致。
  • on 当前全量：data/tx_replay_benchmarks/hotset_ssa_on_current_buildssa_20260519_v3 的 40 条全量基准回放。
  • 额外抽样：data/tx_replay_benchmarks/_tmp_ssa_on_sample_20260519 提供了 phi 连续性问题的直接日志证据。

P0

SSA=ON 改变真实交易行为结果

如何体现：40 条里有 24 条交易的 returncode 与 off 基线不同；ERC-4337 是 8/10，CoW 是 6/10，ERC20 是 5/10，Uniswap V3 也是 5/10。

说明：这说明 SSA 现在不是单纯影响性能，而是在改写真实交易的执行结果。只要这件事没修完，任何 wall time 或 perf 数字都没有解释价值。

修复目标：目标是让这 40 条 prepared replay 在 SSA=ON 与 off 基线下得到完全一致的 returncode。

P0

SSA phi 构造 / 修复仍会生成无效 MIR

如何体现：当前全量基准回放里有 16 条 verifier 报错；最主要的报错是“The number of phi incoming values must match predecessor count”，一共出现了 16 次。抽样还看到了 phi 没有连续放在 block 起始处。

说明：这不是普通日志噪音，而是 MIR 已经不合法。只要 predecessor 集合、incoming 数量和 phi 排布三者对不上，后面的 lowering 和执行结果都不能相信。

修复目标：优先修复 SSA phi 的 predecessor 统计、phi incoming 修补，以及 block rewrite 之后的 phi 连续性。

P0

存在 “verifier error 但最终 returncode=0” 的静默成功风险

如何体现：3 条交易在 SSA=ON 下出现 verifier error，但最终仍返回 0。

说明：这比直接失败更危险，因为表面上看像是成功执行，实际上中间 IR 已经坏了，后面很容易把错误样本当成有效结果。

修复目标：在问题修完前，建议把 verifier failure 直接提升成 hard failure，避免坏样本混进成功样本。

P0

不是所有分叉都能用 verifier error 解释

如何体现：24 条分叉里有 11 条根本没有 verifier error；其中 ERC-4337 bundle 单独就占了 8 条，而且统一表现为 off=2、on=8。

说明：这说明除了 phi/verifier 这一类 bug 之外，至少还存在第二类独立问题，更像是语义分叉或状态码映射出了问题，已经在 bundle / settlement 路径上稳定复现。

修复目标：需要把 ERC-4337、CoW、Uniswap 这批没有 verifier error 的分叉单独拿出来排查，优先看 exit-code mapping、异常传播和 fallback/host 交互路径。

P1

perf-enabled SSA 路径还不可用

如何体现：同一条 prepared replay 在 SSA=OFF 的 perf 构建上可以执行，但 SSA=ON 的旧 perf 目录会 -6 abort，而新的 fresh perf 目录则会在 10ms 内以 109 直接报 CLI 参数解析失败。

说明：这意味着现在根本拿不到可信的 SSA steady-state hotspot profile；任何 profiling 结论都会先被构建或运行时故障污染。

修复目标：先让 perf-enabled SSA build 和普通 Release build 都能稳定执行同一条 prepared command，再回到 x500 / x5000 的 execution hotspot profiling。

P1

部分交易在 SSA=ON 下出现明显 compile-time explosion 症状

如何体现：SSA=ON 当前有 10 条交易的 JIT 超过 5 秒，9 条超过 10 秒，3 条超过 30 秒；最坏样本 JIT 到了 151.7 秒。

说明：这还不能直接解释成单纯的性能退化，因为很多样本本身已经分叉或 verifier fail；但它至少说明 SSA 前端和 phi 修复链路在真实交易上会明显放大编译成本。

修复目标：等正确性问题修完后，优先回看 Uniswap V3 和 ERC20 上的 SSA 前端、CFG 改写、phi 修复以及 JIT suitability 门槛。

修复优先顺序

  1. 先把 SSA phi/verifier 问题清零，特别是 predecessor/incoming count 与 phi contiguity。
  2. 然后单独排查非 verifier 分叉，优先 ERC-4337 bundle 的 2 -> 8 稳定分叉。
  3. 把 verifier error 直接变成 hard failure，避免坏样本混进成功结果。
  4. 修 perf-enabled SSA build，让相同 prepared command 在 on/off perf build 都可跑通。
  5. 最后才重新做 SSA on/off 的性能和 hotspot profiling 对比。
